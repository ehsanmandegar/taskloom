# Taskloom

## مسیر دانش نقش‌ها

در صفحهٔ «نقش‌ها» می‌توان برای تحلیل‌گر، توسعه‌دهنده، آزمونگر و صاحب محصول یک ریشهٔ پوشهٔ دانش تعریف و با «ذخیره مسیرها» ثبت کرد. مسیر باید پوشه‌ای موجود روی دستگاهی باشد که سرور Taskloom روی آن اجرا می‌شود. فایل‌های `*.md` آن پوشه به‌صورت بازگشتی برای تسک‌های همان نقش به عامل معرفی می‌شوند. تسک‌های تازه با نقش تحلیل‌گر آغاز می‌شوند؛ تغییر مرحلهٔ کارت در برد کانبان نقش ذخیره‌شدهٔ تسک را عوض می‌کند و مسیر نقش جدید در پیام‌های بعدی آن تسک استفاده می‌شود. تنظیمات در `~/.taskloom/role-knowledge.json` ذخیره می‌شوند و با `TASKLOOM_ROLE_KNOWLEDGE_PATH` می‌توان محل فایل تنظیمات را تغییر داد.

Taskloom یک داشبورد محلی FastAPI + React است که اجرای تسک‌های مهندسی با Codex یا Claude Code را از ثبت درخواست تا آماده‌شدن یک درخواست ادغام قابل بازبینی مدیریت می‌کند. هدف آن خودکارکردن اجرای عامل انتخاب‌شده است، در حالی که تصمیم نهایی برای commit، push و ایجاد درخواست ادغام در اختیار کاربر باقی بماند.

## چه کاری انجام می‌دهد؟

1. مسیر repository، شناسه تسک، برنچ مبنا، درخواست، راهنماها و دستور اختیاری تست را از یک فرم دریافت می‌کند.
2. تمیزبودن repository را بررسی می‌کند و برنچ `tasks/<task-id>` را دقیقاً از برنچ مبنای انتخاب‌شده می‌سازد.
3. CLI عامل انتخاب‌شده را همراه با راهنماهای پروژه اجرا می‌کند: Codex با sandbox محدود به workspace و Claude Code در حالت `acceptEdits` که نوشتن را به پوشهٔ کاری محدود می‌کند. پس از هر تغییر اجرایی نیز عامل باید مستندات Markdown مرتبط را بازبینی کند، فایل‌های متأثر را به‌روز نگه دارد و اگر تغییری لازم نباشد آن را در خلاصه نهایی اعلام کند.
4. پس از اجرای نخست، گفت‌وگو را با همان عامل و همان شناسهٔ سشن ادامه می‌دهد؛ هر پیام جدید زمینهٔ قبلی را حفظ می‌کند و عامل در صورت نیاز می‌تواند همان برنچ را ویرایش کند. پس از هر پاسخ، تست‌ها دوباره اجرا می‌شوند.
5. خروجی عامل را هنگام اجرا به‌صورت زنده در بخش «تغییرات» و پاسخ در حال نگارش را در گفت‌وگو نشان می‌دهد؛ جهت هر خط متناسب با متن فارسی یا انگلیسی تنظیم می‌شود. پس از اجرا نیز diff، فایل‌های تغییرکرده، تاریخچهٔ گفت‌وگو، خلاصه و خروجی تست در دسترس‌اند. اگر تست ناموفق شود، با «مشاهده جزئیات» کنار پیام خطا، خروجی کامل آخرین اجرای تست نمایش داده می‌شود.
6. فقط پس از موفقیت تست‌ها، commit دستی را فعال می‌کند. پیش از هر push، آخرین وضعیت برنچ مبنا را از `origin` داخل برنچ تسک merge می‌کند تا conflict همان‌جا آشکار و push متوقف شود؛ ایجاد Merge Request نیز تا پس از push غیرفعال می‌ماند. برای پیشنهاد متن commit می‌توانید از دکمهٔ تولید خودکار استفاده کنید؛ متن با همان سشن عامل ساخته و پیش از commit قابل ویرایش است.
7. پنل وضعیت برای Codex اطلاعاتی معادل `/status` و `/model` را از Codex App Server محلی می‌خواند و برای Claude Code وضعیت ورود و provider را از `claude auth status` نشان می‌دهد. اطلاعات حساس حساب مانند token و ایمیل نمایش داده نمی‌شود.

پروفایل‌های پروژه از بالای فرم قابل ذخیره و بازیابی‌اند و برنچ مبنا و نوع عامل (`codex` یا `claude`) را نیز نگه می‌دارند. انتخاب Agent کنار Git hosting انجام می‌شود و پس از شروع اجرا برای همان سشن ثابت است؛ تغییر Codex و Claude وسط سشن پشتیبانی نمی‌شود، چون شناسه و transcript سشن‌های آن‌ها با هم سازگار نیست. برای اجرای بعدی یا سشن جدید می‌توان عامل دیگری انتخاب کرد. این پروفایل‌ها به‌طور پیش‌فرض در `~/.taskloom/profiles.json` نگهداری می‌شوند. برای تغییر محل فایل، متغیر محیطی `TASKLOOM_PROFILES_PATH` را تنظیم کنید. در بخش راهنما می‌توانید علاوه بر فایل، مسیر پوشه وارد کنید؛ همه فایل‌های `.md` آن پوشه و زیرپوشه‌هایش به‌صورت خودکار استفاده می‌شوند.

در Explorer پروژه، فایل‌های Markdown به‌صورت پیش‌فرض با رندر دیداری باز می‌شوند و دکمهٔ چشم/کد در نوار بالای فایل بین پیش‌نمایش و متن منبع جابه‌جا می‌شود. تصویرها و PDFها مستقیماً نمایش داده می‌شوند و متن فایل‌های Word جدید (`.docx`، `.docm` و `.dotx`) نیز بدون اجرای محتوای توکار استخراج و پیش‌نمایش می‌شود؛ قالب قدیمی `.doc` پشتیبانی نمی‌شود.

در اجرای محلی، فرم با مسیر همین repository، قرارداد `04-taskloom-project-contract.md`، فرمان pytest محیط `.venv` و MCP با نام `dws_project` پر می‌شود. برای پروژهٔ DWS، فایل‌های `README.md` و `backend/TESTING_GUIDE.md` به‌همراه تمام Markdownهای `backend/docs` به‌صورت پیش‌فرض استفاده می‌شوند. نبودن یا غیرفعال‌بودن این MCP پیش از ساخت branch اجرا را متوقف می‌کند. در هر profile می‌توان نام MCP و رفتار خطا (`blocked` یا `warning`) را جداگانه ذخیره کرد.

برنچ مبنای پیش‌فرض برای DWS برابر `sandbox` و برای Taskloom برابر `main` است. این مقدار در فرم قابل ویرایش است، همراه profile ذخیره می‌شود و هدف Merge Request نیز قرار می‌گیرد.

بخش «تسک و برنچ» فقط یک ورودی دارد: شمارهٔ تسک را وارد کنید (مثلاً `podw-202`) یا از پیشنهادهای فهرست انتخاب کنید و «ساخت یا سوییچ» را بزنید. Taskloom آن را به `tasks/podw-202` تبدیل می‌کند؛ اگر برنچ از قبل محلی یا روی `origin` وجود داشته باشد فقط آن را checkout می‌کند و وگرنه برنچ تازه را دقیقاً از «برنچ مبنا» فرم می‌سازد (یا از `origin/<base>` اگر مبنا فقط روی remote باشد). همان شماره برای شروع اجرای عامل هم استفاده می‌شود؛ اجرای تسک نیز برنچ موجود را دوباره نمی‌سازد و فقط روی آن checkout می‌کند. این کار هیچ‌وقت `reset` یا `stash` انجام نمی‌دهد؛ بنابراین تغییرات بدون تداخل حفظ می‌شوند و Git در صورت احتمال overwrite شدن فایل‌ها سوییچ را متوقف می‌کند. تا وقتی اجرای عامل برای همان پروژه فعال است، سوییچ برنچ مسدود می‌ماند.

اگر کاربر مسیر پروژه را عوض کند، مقادیر پیش‌فرض راهنما، تست و MCP پاک می‌شوند تا قرارداد Taskloom روی پروژهٔ دیگر اعمال نشود؛ مقادیری که کاربر سفارشی کرده است حفظ می‌شوند. هر repository دیگری را هم می‌توان مستقیم انتخاب یا به‌عنوان profile ذخیره کرد. برای تغییر پیش‌فرض‌ها از `TASKLOOM_DEFAULT_PROJECT_PATH`، `TASKLOOM_DEFAULT_GUIDE_PATHS` (جداشده با path separator سیستم)، `TASKLOOM_DEFAULT_TEST_COMMAND`، `TASKLOOM_DEFAULT_MCP_SERVER`، `TASKLOOM_DEFAULT_MCP_FAILURE_MODE`، `TASKLOOM_DEFAULT_BASE_BRANCH` و `TASKLOOM_DEFAULT_AGENT_TYPE` استفاده کنید.

برای پروژهٔ DWS، گزینهٔ «پیش از اجرای تست، setup دیتابیس محلی را خودکار اجرا کن» را می‌توان در profile ذخیره کرد. با فعال‌سازی آن، Taskloom پیش از شروع عامل و درست پیش از gate تست نهایی، دیتابیس تست محلی را reset می‌کند، bootstrap ورود کاربران را تا سه تلاش انجام می‌دهد و `scripts/grant_local_test_admin.py` را با interpreter محیط مجازی `backend` اجرا می‌کند. تب «Setup تست» نیز همین عملیات را با تأیید دوبارهٔ کاربر اجرا می‌کند. این قابلیت فقط `TEST_DATABASE_URL` با host محلی را می‌پذیرد و خروجی حساس اسکریپت‌ها را نمایش نمی‌دهد.

دستور تست و «پوشهٔ کاری تست» جداگانه ذخیره می‌شوند. مسیرهای نسبی دستور از همان پوشهٔ کاری محاسبه می‌شوند و این پوشه باید داخل repository باشد. اگر دستور مشخص نشده باشد و `package.json` یک script به نام `test` داشته باشد، Taskloom همان `npm test` را اجرا می‌کند؛ صرف وجود پوشهٔ `tests/` در یک پروژهٔ Node باعث انتخاب pytest نمی‌شود. برای DWS، پیش‌فرض `backend` است و Taskloom فرمان `.\venv\Scripts\python.exe -m pytest` را از آن اجرا می‌کند؛ بنابراین interpreter متعلق به بک‌اند است. نشست‌ها و profileهای قدیمی DWS که با `python -m pytest -q` ذخیره شده‌اند، هنگام بارگذاری به این تنظیم مهاجرت می‌شوند.

## نگه‌داری و ادامهٔ گفت‌وگو

هر اجرا به‌صورت یک سشن جدا همراه با نوع عامل ذخیره می‌شود. از منوی «گفت‌وگوهای اخیر» می‌توان یک سشن قبلی را باز کرد و با همان زمینه و همان عامل پیام داد؛ اگر درخواست نیاز به تغییر داشته باشد، عامل همان branch را ویرایش و تست‌ها را دوباره اجرا می‌کند. در کادر پیام، Enter پیام را ارسال و Shift+Enter خط جدید ایجاد می‌کند؛ متن پاسخ و فعالیت‌های عامل با یک اتصال رویداد زنده نمایش داده می‌شوند و polling نیز مسیر جایگزین است. آخرین سشن بازشده پس از رفرش صفحه نیز بازیابی می‌شود.

فهرست سشن‌ها حتی پس از رسیدن یک اجرا به وضعیت نهایی به‌صورت دوره‌ای همگام می‌شود؛ بنابراین اگر همان سشن یا سشن دیگری با Todo بعدی دوباره وارد صف شود، وضعیت، پیام‌های گفت‌وگو و پاسخ عامل بدون refresh دستی نمایش داده می‌شوند. شمارندهٔ «کارهای بعدی» مجموع Todoهای pending همهٔ سشن‌ها را نشان می‌دهد.

تاریخچهٔ سشن‌ها به‌طور پیش‌فرض در `~/.taskloom/sessions.json` نگه‌داری می‌شود. برای تغییر محل آن، متغیر محیطی `TASKLOOM_SESSIONS_PATH` را تنظیم کنید. اگر برنامه هنگام پاسخ عامل بسته شود، آن سشن در فهرست باقی می‌ماند و می‌توانید بعداً همان session ID را با همان عامل ادامه دهید.

در زمان اجرای عامل یا تست‌ها می‌توان اجرای فعال را با دکمهٔ «توقف» قطع کرد. اگر session ID عامل ایجاد شده باشد، کادر گفتگو بلافاصله فعال می‌شود تا اصلاحیه در همان سشن ارسال و کار از همان زمینه ادامه داده شود.

## راه‌اندازی

پیش‌نیازها: Python 3.10+، Node.js 18+، Git و دست‌کم یکی از Codex CLI یا Claude Code CLI که قبلاً login شده باشد. برای Claude Code از `claude auth status` و برای Codex از login خود CLI می‌توان وضعیت را بررسی کرد. برای ایجاد درخواست ادغام، متناسب با سرویس remote باید GitHub CLI (`gh`) یا GitLab CLI (`glab`) نیز نصب و وارد حساب شده باشد.

اگر Claude Code روی ویندوز پیام `claude native binary not installed` یا ناسازگاری executable نشان داد، نصب npm ناقص است: optional dependency یا postinstall اجرا نشده است. از پوشهٔ نصب global فرمان `node node_modules/@anthropic-ai/claude-code/install.cjs` را اجرا کنید یا بسته را بدون `--ignore-scripts` و `--omit=optional` دوباره نصب کنید، سپس `claude --version` و `claude auth status` را بررسی کنید. Taskloom متن خطای CLI پیش از ساخته‌شدن سشن را مستقیماً نمایش می‌دهد.

```powershell
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
Set-Location frontend
npm.cmd install
npm.cmd run build
Set-Location ..
.venv\Scripts\python.exe main.py
```

نسخه build شده روی `http://localhost:8003` در دسترس است. برای توسعه UI، در ترمینال دوم `Set-Location frontend; npm.cmd run dev` را اجرا کنید؛ Vite درخواست‌های `/api` را به FastAPI می‌فرستد.

برای اجرای هم‌زمان چند نمونه، به هرکدام پورت جدا بدهید. سشن‌ها و پروفایل هر پورت به‌طور خودکار در پوشه‌ای جدا ذخیره می‌شوند و با نمونه‌های دیگر مخلوط نمی‌شوند:

```powershell
.venv\Scripts\python.exe main.py --port 8003
.venv\Scripts\python.exe main.py --port 8004
```

پورت پیش‌فرض ۸۰۰۳ برای سازگاری، داده‌های قبلی `~/.taskloom` را نگه می‌دارد؛ پورت‌های دیگر از `~/.taskloom/instances/port-<port>` استفاده می‌کنند. با `--data-dir C:\path\to\instance` می‌توان محل دادهٔ یک نمونه را صریح تعیین کرد و با `--no-browser` از بازشدن خودکار مرورگر جلوگیری کرد. در خود داشبورد نیز دکمهٔ `+` یک تب کاری مستقل می‌سازد؛ فرم، تنظیمات، سشن، پیام در حال نگارش و وضعیت اجرای هر تب مستقل است و جابه‌جایی بین تب‌ها اجرای پس‌زمینه را متوقف نمی‌کند. تسک‌های دو پروژه یا دو Git worktree می‌توانند موازی اجرا شوند؛ Taskloom شروع دو اجرای هم‌زمان روی یک مسیر فیزیکی repository را رد می‌کند تا checkout و فایل‌های آن‌ها با هم تداخل نکنند. همین قاعده را هنگام اجرای چند process روی پورت‌های متفاوت نیز رعایت کنید، چون جداسازی پورت مربوط به داده‌های Taskloom است، نه فایل‌های repository.

### ساخت فایل اجرایی ویندوز

روی ویندوز دستور `python build_exe.py` را اجرا کنید. این اسکریپت وابستگی‌ها و فرانت‌اند را build می‌کند و سپس یک خروجی مستقل در `dist\Taskloom.exe` می‌سازد. اجرای فایل exe سرور محلی را راه‌اندازی و Taskloom را در مرورگر باز می‌کند. برای ساخت خروجی، Python 3.10+ و Node.js 18+ لازم است؛ سیستم مقصد برای اجرای خود exe به Python یا Node.js نیاز ندارد، اما Git و CLI عامل انتخابی باید نصب و قبلاً وارد حساب شده باشند.

> این ابزار برای اجرای محلی و کاربر مورد اعتماد طراحی شده است؛ آن را بدون احراز هویت روی اینترنت منتشر نکنید.

## دسترسی به راهنماها با MCP

یک MCP server فقط‌خواندنی در پروژه وجود دارد که فایل‌های Markdown را به‌صورت resource و با سه ابزار `list_guides`، `read_guide` و `search_guides` ارائه می‌کند. فایل `mcp-config.example.toml` نمونه تنظیم پروژه‌ای برای Codex است؛ جدول آن را در `.codex/config.toml` یک repository مورد اعتماد قرار دهید، Codex را از ریشه پروژه باز کنید و کلاینت را restart کنید. برای Claude Code همان سرور را از ریشه repository با `claude mcp add taskloom_guides --scope project -- python -m backend.app.guide_mcp --root .` ثبت کنید. سپس با `codex mcp get taskloom_guides --json` یا `claude mcp get taskloom_guides` اتصال عامل انتخابی را بررسی کنید.

برای اجرای مستقیم یا استفاده در یک MCP client دیگر:

```powershell
python -m backend.app.guide_mcp --root .
```

گزینه `--root` می‌تواند مسیر یک فایل Markdown یا پوشه باشد و برای چند مسیر قابل تکرار است. سرور فقط فایل‌های `.md` کشف‌شده در همین ریشه‌ها را می‌خواند و به فایل‌های بیرون از آن‌ها دسترسی نمی‌دهد.
